## 結論: コアリポジトリに、AI向けの開発規約が2,500行入りました

EC-CUBE 4.4 のリポジトリには、人間が読むための README とは別に、AIエージェントが読むための規約が置かれています。

- `AGENTS.md`（309行）
- `.claude/skills/` 配下に 19個のスキル（合計2,503行）

[#6817](https://github.com/EC-CUBE/ec-cube/pull/6817) で基盤が入り、[#6853](https://github.com/EC-CUBE/ec-cube/pull/6853) でレイヤ別スキルが追加され、[#6907](https://github.com/EC-CUBE/ec-cube/pull/6907) で定義ファイルの配置原則がまとまりました。

これは EC-CUBE を使う人にとっては直接関係のない変更です。ただし自分のプロジェクトで同じことをやるときの参考資料としては、かなり見応えがあります。とくに「AI向けドキュメントをどこに何個置くか」で悩んだことがあるなら、答えの一例がここにあります。

**TL;DR**

- `AGENTS.md` を正典（ハブ）とし、`CLAUDE.md` / `GEMINI.md` は `@./AGENTS.md` を指す薄いポインタ
- ポインタは「`AGENTS.md` をネイティブに読まないツールにだけ置く」という原則を明文化
- Cursor / Copilot / Codex CLI は `AGENTS.md` を直接読むので**専用ファイルを作らない**
- スキルの正本は `.claude/skills/`。`.codex/skills` と `.agents/skills` は symlink。同期スクリプト不要
- スキルは19個。`security` `purchase-flow` `entity` などレイヤ別
- 中身の主眼は「ツールでは検出できない観点」。PHPStan や php-cs-fixer で分かることは書かない

## なぜ AI向けの規約が要るのか

コーディング規約なら PHPStan と php-cs-fixer で機械的に守れます。わざわざ自然言語で書く必要はありません。

書かれているのは、**静的解析では検出できない知識**です。

`AGENTS.md` の「ドメイン用語（ツールでは読み取れない知識）」という節が、その典型です。

> **受注ステータス（OrderStatus, `mtb_order_status`）** — （中略）
> **注意: `PROCESSING`・`PENDING` は「確定前の仮受注」**。カート確定の入口で `OrderHelper` が受注を `PROCESSING` で作り、
> 購入完了で `NEW` に遷移する。売上集計や受注一覧はこれらを除外する（`OrderStatusFilter`）。
> 「`Order` が存在する＝確定済み注文」と誤解しないこと。

EC-CUBE を触っていると、これが実際に事故る箇所だと分かります。`dtb_order` を素直に集計すると、カートに入れただけの仮受注が売上に混ざります。

こういう知識は、コードを読んでも分かりません。`OrderStatus::PROCESSING` という定数を見ても「処理中なんだろう」としか思えない。**ドメインの意味は型に現れない**からです。

他にもこんな項目が並びます。

> **ProductClass と「規格なし商品」** — 在庫・価格は `Product` ではなく `ProductClass` 単位で持つ。
> **規格（サイズ・カラー）を持たない商品も、内部的に `ProductClass` を 1 つ持つ**

> **単一テーブル継承（STI）と `discriminator_type`** — （中略）**INSERT 時はこの列の指定が必須**
> （例: `mtb_sale_type` は `'saletype'`、`dtb_block` は `'block'`）

どれも、知らずに書くと動かないか、静かに間違うものです。新しく参加した人間の開発者に説明する内容と、ほぼ同じでもあります。

## 定義ファイルを増やさないという原則

個人的に一番参考になったのが #6907 で入った、この原則です。

> **ポインタ定義ファイルは「`AGENTS.md` をネイティブに読まないツール」にだけ置く。** それ以外は正典を二重に指すだけの冗長ファイルになるため作らない。
> - 必要な例: Claude Code → `CLAUDE.md`、Gemini CLI → `GEMINI.md`（いずれも `AGENTS.md` をネイティブに読まない）。
> - 不要な例: **Cursor / GitHub Copilot / Codex CLI は `AGENTS.md` をネイティブに読む**ため、`.cursor/rules/*` や `.github/copilot-instructions.md` は追加しない。

AI向けの設定ファイルは、放っておくと増えます。`.cursorrules`、`.github/copilot-instructions.md`、`CLAUDE.md`、`GEMINI.md`、`.windsurfrules`。ツールが増えるたびに1つずつ足していくと、同じ内容のファイルが5個並ぶことになります。

そして必ず同期が崩れます。片方だけ更新して、もう片方が古いまま残る。どれが正しいのか誰も分からなくなります。

EC-CUBE の答えは「ツールがネイティブに読むファイルだけ置き、中身は正典へのポインタにする」でした。実際 `CLAUDE.md` は14行しかありません。

```markdown
# CLAUDE.md

このファイルは [`AGENTS.md`](./AGENTS.md) を参照する薄いポインタです。

プロジェクトの開発ガイド（技術スタック・ディレクトリ構成・開発コマンド・アーキテクチャ）、
コーディング規約、AI エージェント向けの指示はすべて **`AGENTS.md`（正典）** に集約しています。
まず `AGENTS.md` を読み込んでから作業してください。

@./AGENTS.md
```

`@./AGENTS.md` は Claude Code のファイル参照記法です。実質的な内容はゼロで、正典を読ませるためだけに存在します。

新しい定義ファイルを足すときはインデックス表にも1行追加するというルールまで決まっています。所在を1箇所で管理する、という意思です。

## symlink でスキルを共有する

もう1つの工夫が、スキルの配置です。

Claude Code は `.claude/skills/`、Codex CLI は `.codex/skills/`、Google Antigravity は `.agents/skills/` を読みます。ディレクトリ名がツールごとに違います。

素直にやるならコピーして同期しますが、EC-CUBE は symlink を選びました。

```
.agents/skills -> ../.claude/skills
.codex/skills  -> ../.claude/skills
```

実際にリポジトリを見ると、`.agents/` と `.codex/` の中身は symlink 1本だけです。

> 各 Skill の本文は `.claude/skills/<name>/SKILL.md` が直接保持します（薄いスタブと本文を分ける二層は廃止）。
> `.codex/skills` `.agents/skills` は `.claude/skills` への **symlink**（`../.claude/skills`）で、正本は常に 1 つ。
> コピー同期スクリプトや同期 CI は不要です

「薄いスタブと本文を分ける二層は廃止」という記述から、一度は別の構成を試して戻したことが読み取れます。

:::message alert
symlink には前提があります。ドキュメントにも書かれているとおり、**Windows では git の symlink サポート（`core.symlinks=true`）か Developer Mode が必要**です。Windows 環境のコントリビューターがいるプロジェクトで真似する場合は、ここを確認してください。
:::

### スキルの中身

`security` スキルを見ると、書き方の方針が分かります。

```markdown
---
name: security
description: EC-CUBE 4.4 の認証・認可・CSRF などセキュリティを実装・改修・点検するときの規約。
「認可を追加して」「アクセス制御を直して」「このルートに権限チェックを入れて」…
または src/Eccube/Security 配下・app/config/eccube/packages/security.yaml を作成・編集するとき…
---
```

`description` に**発動条件が具体的に書かれています**。「〜と言われたとき」「〜のファイルを編集するとき」。エージェントがどのタイミングでこのスキルを読むべきかを、曖昧さなく指定しています。

セクション構成も一貫しています。

```
## アクセス制御モデル（まず全体像を掴む）
## 基本ルール
## 実装パターン
## よくある間違い（認可・CSRF・IDOR — ツールでは検出できない観点）
## 実行・確認方法
```

「よくある間違い」の見出しに「ツールでは検出できない観点」と明記されているのが、この文書群の性格をよく表しています。PHPStan が拾えるものは書かない。人間のレビューでしか気づけないものを書く。

## 「推測実装の禁止」という基本原則

`AGENTS.md` の末尾にある「基本原則」が、実は一番効いていると思います。

> - **推測実装の禁止**: 「〜のはず」で書かず、必ず既存コード・ドキュメントで裏取りする。

これは AI に向けた指示として、極めて的確です。LLM は知らないことを聞かれると、**もっともらしい嘘を書きます**。EC-CUBE のような大きなフレームワークでは、存在しないメソッドや、他のフレームワークの作法が混ざったコードが出てきます。

「裏取りしろ」と明示しておくと、実際に挙動が変わります。自分もこのリポジトリの記事を書くとき、PR 本文だけを読んで書いた箇所が後から間違っていたことがありました。一次ソースを見に行く手間を惜しむと、確実に事故ります。

もう1つ、バージョン体系についての記述も面白い項目です。

> **含意**: `4.3→4.4` は「マイナー」ではなく**メジャー**。`@deprecated` な public API / interface / Entity ゲッタの撤去は、
> こうしたメジャーの節目でなら実施可能な破壊的変更であり、「次の 5.0 まで技術的に不可」ではない。
> （中略）負債やレビューで「BC ロック＝修正不可」と機械的に断じないこと。

AI が保守的すぎる判断をするのを防ぐための記述です。「後方互換のため変更できません」と機械的に答えるのを封じています。バージョン番号の見た目（4.3 → 4.4）から「マイナーだから壊せない」と推論されるのを、明示的に否定しているわけです。

規約というより、判断の前提を揃えるための文書になっています。

## 自分のプロジェクトに持ち込むなら

EC-CUBE の構成をそのまま真似する必要はありませんが、考え方は流用できます。

**書くべきは、コードを読んでも分からないことです。** 命名規則やインデントは Linter に任せる。ドメイン用語の意味、ステータスの落とし穴、テーブル設計の暗黙の前提。この3つだけでも書いておくと、人間の新メンバーにも効きます。

**定義ファイルは増やさないルールを先に決めてください。** ツールが増えるたびに設定ファイルを足すと、同期が崩れて誰も信用しなくなります。正典を1つ決めて、他はポインタにする。EC-CUBE の `CLAUDE.md` が14行なのは、そういう判断の結果です。

**発動条件を description に書いてください。** 「〜のとき使う」を具体的に列挙しておくと、エージェントが適切なタイミングで読みます。逆にここが曖昧だと、書いても読まれません。

**「推測禁止」は入れる価値があります。** 一行足すだけで、裏取りの頻度が変わります。

## まとめ

- EC-CUBE 4.4 のリポジトリに、AI向けの開発規約が `AGENTS.md`（309行）+ スキル19個（2,503行）で入った
- 書かれているのは静的解析で検出できない知識。ドメイン用語、ステータスの落とし穴、STI の暗黙の前提など
- `AGENTS.md` を正典とし、`CLAUDE.md` / `GEMINI.md` は薄いポインタ。ネイティブに読まないツールにだけ置くという原則を明文化
- スキルの正本は `.claude/skills/`。`.codex` `.agents` は symlink で共有し、同期スクリプトを不要にした（Windows では symlink サポートが前提）
- スキルはレイヤ別に分割。`description` に発動条件を具体的に書く
- 「推測実装の禁止」「4.3→4.4 はメジャー」など、AI の判断の前提を揃える記述が含まれる

OSS のリポジトリに AI向けの規約が入るのは、まだ珍しい段階です。中身が公開されていて、いつでも読めるというのがありがたいところで、自分のプロジェクトで同じことをやるときの叩き台になります。
