## 結論: プラグインで実装していた機能が、3つ本体に入ります

EC-CUBE 4.4 には、DBAL 4 対応やエージェントコマースのような大物の陰で、**現場の運用で効く小さめの機能**がいくつか入っています。

いずれも「プラグインを入れるか、自分で作るか」で悩んでいた類のものです。

| 機能 | PR | 追加行数 |
| --- | --- | --- |
| 受注管理用メモ | [#6840](https://github.com/EC-CUBE/ec-cube/pull/6840) | +614 |
| 配送方法・支払い方法の保存と復元 | [#6833](https://github.com/EC-CUBE/ec-cube/pull/6833) | +1,792 |
| マイページに追跡番号を表示 | [#6826](https://github.com/EC-CUBE/ec-cube/pull/6826) | +284 |

**TL;DR**

- 商品に「受注管理用メモ」を設定すると、注文確定時に**受注明細へスナップショットとしてコピー**される
- 会員が使った配送方法・支払い方法を保存し、次回**ボタンを押したときだけ**復元する（自動適用しない）
- マイページの注文履歴詳細に、出荷のお問い合わせ番号（追跡番号）が表示される
- 同種のプラグインを入れている場合、機能が重複する可能性がある

## 受注管理用メモ（#6840）

商品マスタに「受注管理用メモ」を持たせ、その商品が注文されたときに受注明細へコピーする機能です。

「この商品は冷凍便で送る」「同梱不可」「熨斗の対応が必要」といった、**出荷担当への申し送り**を商品ごとに登録しておく用途を想定しています。

### 実装のポイントはスナップショット

面白いのは、参照ではなく**コピー**である点です。`OrderMemoPreprocessor` を見ると意図が明確に書かれています。

```php
class OrderMemoPreprocessor implements ItemHolderPreprocessor
{
    #[\Override]
    public function process(ItemHolderInterface $itemHolder, PurchaseContext $context): void
    {
        if (!$itemHolder instanceof Order) {
            return;
        }

        foreach ($itemHolder->getOrderItems() as $OrderItem) {
            // 商品明細のみ対象(送料・手数料・値引き等は対象外)
            if (!$OrderItem->isProduct()) {
                continue;
            }

            $Product = $OrderItem->getProduct();
            if ($Product === null) {
                continue;
            }

            // 確定時点の商品メモを明細へスナップショットとしてコピー(常に上書き).
            // メモが未設定(null)の商品では明細メモも null になる.
            $OrderItem->setOrderMemo($Product->getOrderMemo());
        }
    }
}
```

商品マスタのメモを後から書き換えても、**過去の受注のメモは変わりません**。注文時点の指示が残ります。

これは受注データの設計として正しい判断です。EC-CUBE では商品名や価格も同じように受注明細にコピーされます。商品マスタを変更したら過去の注文の金額まで変わった、では困るからです。メモも同じ扱いにしたということです。

`isProduct()` で商品明細だけに絞っているのも要点です。送料・手数料・値引きの明細には `Product` がないので、そこは対象外にしています。

### プラグイン開発者への影響

`ItemHolderPreprocessor` として実装されているので、**PurchaseFlow に処理が1つ増えます**。

自作のプリプロセッサが受注明細を走査している場合、`order_memo` という新しいプロパティが増えたことになります。明細を独自にコピーしているコードがあれば、メモが引き継がれるか確認してください。

商品 CSV のインポートテンプレートにもカラムが追加されました。[PR #6960](https://github.com/EC-CUBE/ec-cube/pull/6960) は、この変更でテストが落ちた分の回帰修正です。**商品 CSV を自動生成・自動取り込みしているバッチがあるなら、列が増える点に注意してください。**

## 配送方法・支払い方法の保存と復元（#6833）

会員が注文手続きで使った配送方法と支払い方法を保存し、次回以降に復元できる機能です。

`Customer` エンティティにカラムが追加されています。

```php
#[ORM\JoinColumn(name: 'preferred_payment_id', referencedColumnName: 'id', onDelete: 'SET NULL')]
// ...
#[ORM\JoinColumn(name: 'preferred_delivery_id', referencedColumnName: 'id', onDelete: 'SET NULL')]
```

`onDelete: 'SET NULL'` が付いています。管理画面で支払方法を削除しても、会員レコードが壊れずに参照だけ外れます。地味ですが必要な配慮です。

### 自動適用しないという判断

この機能で最も重要な設計判断は、**復元を自動でやらない**ことです。

保存済みの会員には注文手続き画面に「保存された設定があります」という情報ボックスが出て、「この設定を使用する」ボタンを押したときだけ適用されます。押さなければ通常どおりの初期選択です。

自動適用しない理由は想像がつきます。**前回と同じ支払方法が今回も使えるとは限らない**からです。金額が変わって利用条件から外れる、支払方法が非公開になる、といったことが起きます。

実際、保存された支払方法が使えない場合は、情報ボックスの代わりに警告が出る作りになっています。

対象は**会員のみ・単一配送先のみ**です。ゲスト購入と複数配送先は対象外。保存は会員1人につき1組で、上書きされます。

### 影響範囲

`Customer` にカラムが2つ増えるので、**会員 CSV のエクスポート項目が変わる可能性があります**。会員データを外部システムと同期しているなら確認が要ります。

注文確認画面（`/shopping/confirm`）に「この配送方法と支払い方法を保存する」チェックボックスが追加されるため、**確認画面のテンプレートを上書きしているサイトは表示崩れに注意**してください。合計金額と「注文する」ボタンの間に入ります。

## マイページに追跡番号を表示（#6826）

`Shipping` にはもともと「お問い合わせ番号」（追跡番号）のカラムがあり、管理画面から入力できました。ただし**フロントの注文履歴には出ていませんでした**。

4.4 でマイページの注文履歴詳細に表示されます。

```twig
{% if Shipping.tracking_number %}
    <dt>{{ 'front.mypage.tracking_number'|trans }} :</dt>
    <dd>{{ Shipping.tracking_number }}</dd>
{% endif %}
```

番号が入っているときだけ表示する、素直な実装です。

なぜ今までなかったのか、と言いたくなる機能です。管理画面で入力できるのにお客様には見えないので、問い合わせのたびに手作業でメールするか、プラグインで表示するしかありませんでした。

### 表示するだけで、リンクにはなりません

番号を表示するだけで、配送業者の追跡ページへのリンクにはなりません。配送業者ごとに URL が違うため、汎用的に作れないという判断でしょう。

リンクにしたい場合は `Delivery` に業者を判別する情報を持たせて、テンプレートで組み立てることになります。テンプレートのカスタマイズで対応できる範囲です。

## プラグインと重複しないか確認を

3機能とも、**同じことをするプラグインが既に存在します**。4.4 に上げると機能が二重になる可能性があります。

| 4.4 の機能 | 確認すること |
| --- | --- |
| 受注管理用メモ | 商品に独自メモ欄を足すプラグインを入れていないか。カラム名が衝突しないか |
| 配送・支払方法の保存 | 会員の「お気に入り決済」的なプラグインがないか |
| 追跡番号表示 | マイページに追跡番号を出すプラグインを入れていないか。二重表示にならないか |

とくに受注管理用メモは、`Product` と `OrderItem` にカラムが増えます。プラグインが `EntityExtension` で同名のプロパティを追加していると、**proxy 生成時に衝突する可能性があります**。プラグイン側のカラム名を確認しておくと安全です。

追跡番号の表示は、プラグインがテンプレートを上書きしている場合、そちらが優先されるので二重表示は起きにくいはずです。ただしテンプレートの上書き方によっては両方出ます。

## まとめ

- **受注管理用メモ**（[#6840](https://github.com/EC-CUBE/ec-cube/pull/6840)）: 商品のメモを注文確定時に受注明細へスナップショットコピー。商品マスタを後から変えても過去の受注は変わらない
- **配送・支払方法の保存と復元**（[#6833](https://github.com/EC-CUBE/ec-cube/pull/6833)）: 会員のみ・単一配送先のみ。**自動適用せずボタンで明示的に復元**する。使えない場合は警告を出す
- **追跡番号の表示**（[#6826](https://github.com/EC-CUBE/ec-cube/pull/6826)）: マイページの注文履歴詳細に表示。リンクにはならない
- 商品 CSV・会員 CSV の項目が増える可能性がある。自動連携しているなら確認を
- 同種のプラグインとの重複、とくに `EntityExtension` によるカラム名の衝突に注意

派手さはありませんが、どれも問い合わせ対応や出荷作業の手間に直結します。プラグインで賄っていたものが本体に入ると、バージョンアップのたびに追従する手間が減るのが一番の価値だと思います。
