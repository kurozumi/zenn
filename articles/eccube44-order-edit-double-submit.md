## 結論: あなたも「登録」ボタンを2回押したこと、ありませんか?

保存に時間がかかる画面で、反応が返ってこないので焦ってもう一度ボタンを押す――誰もが一度はやったことのある操作です。EC-CUBEの管理画面ではこれが、受注明細(`OrderItem`)の静かなデータ破損につながることがあります。しかも壊れ方が地味なため、気づかれないまま本番DBに残り続けている可能性があります。

原因は、保存ボタンの「送信中はロックする」という演出が、**サーバーの応答を待たずに一定時間で勝手に解除される**という実装上の隙です。そしてより意外なのは、**CSRFトークンがあってもこの二重送信は防げない**という事実です。

この不具合は EC-CUBE 4.4(未リリース)で修正されますが、興味深いのは「本格的な楽観的ロック」ではなく、あえて最小限の対策を選んだ設計判断です。この記事では、Issue報告からPRの修正内容まで一次ソースを追いながら、「なぜこの不具合が起きるのか」「なぜCSRFトークンだけでは防げないのか」「本体はなぜ本格的な楽観的ロックを入れなかったのか」を読み解きます。

**TL;DR**
- EC-CUBEの管理画面、保存ボタンを短時間に2回押すと受注明細が壊れることがある([Issue #6671](https://github.com/EC-CUBE/ec-cube/issues/6671))。しかも壊れ方が地味で気づきにくい(送料明細に古い商品コードが紐づく、等)
- **CSRFトークンでは二重送信を防げない**。Symfonyの`CsrfTokenManager`はトークンを検証後も無効化しないため、同じトークンで何度でもPOSTできる(CSRF対策自体は引き続き必須で、これはCSRFの不備ではなく目的の異なる別問題)
- JS側でボタンを無効化するだけでも不十分。XHR(Ajax)で直接同じエンドポイントを叩けばガードは素通りする
- EC-CUBE 4.4はこの問題を、**Doctrineの本格的な楽観的ロックではなく**「隠しフィールドで更新日時を比較する」という最小限の対策で塞ぐ([PR #6903](https://github.com/EC-CUBE/ec-cube/pull/6903)、`4.4` ブランチにマージ済み)
- **現時点(2026年7月)で EC-CUBE 4.4 は未リリース**。4.1〜4.3系(リリース済みの全バージョン)ではこの不具合は未修正

## この記事の位置づけ(重要)

修正PRは EC-CUBE 本体リポジトリの [PR #6903](https://github.com/EC-CUBE/ec-cube/pull/6903) として実装され、**`4.4` ブランチに2026年7月15日マージ済み**です。関連する [Issue #6671](https://github.com/EC-CUBE/ec-cube/issues/6671) 自体は、この記事の調査時点でも **Close(クローズ)されていません**(PRの説明文が "Fixes #6671" ではなく "Refs #6671" になっているため、マージによる自動クローズが発生していません)。つまり不具合自体はIssueとして現役です。

Issueの報告では EC-CUBE 4.1.2 での再現が報告されており、報告者は `function.js` の該当実装が同じであることから4.2/4.3系でも同様の問題が起きると推測しています。PR本文で実際に再現が確認されているのは4.4での話です。**4.3系を含め、この記事執筆時点でリリース済みのバージョンにはまだこの修正は入っていません。**実際のリリース時には細部が変わる可能性がある点にご注意ください。

## 何が起きるのか: Laddaの2秒タイムアウト

管理画面の受注編集画面の保存ボタンには、連打防止のために [Ladda](https://laadd.com/)というJSライブラリでローディング演出が付けられています。該当箇所は `html/template/admin/assets/js/function.js` で、次のような設定です。

```js
Ladda.bind('button[type=submit],a[token-for-anchor]', { timeout: 2000 });
```

`timeout: 2000` は「2000ミリ秒経ったら、サーバーからの応答が来ていなくてもボタンを再度押せる状態に戻す」という設定です。本来は「万一サーバーが無応答のまま固まった場合に、ユーザーがずっとボタンを押せなくなる事態を避ける」ためのフェイルセーフですが、これが裏目に出ます。**受注データが大きく、保存処理に2秒以上かかる場合、ユーザーがまだ処理中の画面を見て「反応がない」と誤解し、再度ボタンを押してしまう**のです。

## なぜこれがデータ破損につながるのか

単に「同じ内容がもう一度保存される」だけなら実害は軽微です。しかし実際には、1回目の送信がDBに反映された後に2回目の送信が処理されることで、**POSTデータのインデックスとDB上のレコードがずれる**という、より深刻な壊れ方をします。

Issue #6671 で報告されている具体例で見てみます。ある受注に商品明細が6行ある状態から、ユーザーが編集画面で新しい商品を1行追加して保存したケースです。

1. 1回目の送信で商品行が追加され、DB上の `OrderItem` は7行になる(新しい行にはIDが振られる)
2. しかし2回目の送信は、**1回目の送信が始まる前の画面(まだ6行だった状態)のPOSTデータ**を送ってしまう
3. サーバー側の `OrderType::sortOrderItems` は、POSTされた明細を種別→IDの順で並べ替えて、**現在のDB状態(7行)に対して**位置合わせをする
4. その結果、本来「送料明細」だったはずのPOSTデータが、1回目の送信で新しく作られた商品行に上書きされてしまう
5. さらに、POSTデータ側には存在しない行が `allow_delete` の設定によって削除されたり、逆に余分な行が新規作成されたりする

`product_id` や `product_code` はフォームのマッピング対象外のフィールドなので、上書きされた後も古い商品の識別情報だけが残ります。結果として、「送料の金額なのに商品コードが紐づいている」といった、見た目では気づきにくい壊れ方をした `OrderItem` レコードがDBに残ってしまいます。

## 素朴な対策では防げない理由

「じゃあボタンを押した瞬間にJS側で無効化すればいいのでは」と思うかもしれません。実際、修正PRにもこの対策は含まれています。しかしPR本文では、この対策だけでは不十分だと明言されています。理由は、**ブラウザの標準的なフォーム送信を経由しない、XHR(Ajax)による二重送信は、JS側のボタン無効化だけでは防げない**ためです。実際、Issueの報告者自身が、同じ内容のPOSTリクエストを2本同時に送りつける再現スクリプトを提示しています。ブラウザの見た目上は1回しかボタンを押していなくても、開発者ツールや外部ツールから同じエンドポイントに直接リクエストを送れば、JS側のガードは意味を持ちません(なお受注編集画面は管理者ログインが前提の機能であり、この再現には既に管理画面へのアクセス権限が必要です)。

CSRFトークンも解決策にはなりません。Symfonyの `CsrfTokenManager::isTokenValid()` の実装を見ると、トークンが検証に使われた後も**明示的に無効化する処理は行われず**、ストレージ(セッション)に保存された値との比較のみで判定されます。つまり同一セッション内であれば、同じCSRFトークンを使って複数回POSTを送ることが可能です。これはCSRFトークンの不備ではなく、**CSRF対策(サイトをまたいだ偽装リクエストの防止)と二重送信対策はそもそも目的が異なる別の仕組みだから**です。CSRF対策自体は引き続き必須であり、今回の問題は「CSRFを通過した正規のリクエストが、意図せず2回送られてしまう」という別レイヤーの話です。

## 修正の中身: 二層防御

PR #6903 では、次の2層の対策が実装されています。

### レイヤー1(サーバー側・本命): 更新日時の不一致チェック

`OrderType.php` に、DBにマッピングされない隠しフィールド `form_update_date` が追加されます。フォーム描画時、このフィールドには**そのときの受注の `update_date`** が埋め込まれます。

```php
// OrderType.php: 既存の sortOrderItems と同様、POST_SET_DATA リスナーとして登録される
$builder->addEventListener(FormEvents::POST_SET_DATA, $this->keepFormUpdateDate(...));

// 送信されたインデックスと DB 上の明細順がずれてデータが破損するのを防ぐため,
// コントローラ側で描画時点と現在の更新日時を突合する. (Issue #6671)
public function keepFormUpdateDate(FormEvent $event): void
{
    /** @var Order|null $Order */
    $Order = $event->getData();
    if (null === $Order || null === $Order->getUpdateDate()) {
        return;
    }

    $event->getForm()->get('form_update_date')->setData(
        $Order->getUpdateDate()->format('Y-m-d H:i:s')
    );
}
```

保存処理(`EditController::register`)では、送信されてきた `form_update_date` と、**その時点でDBに保存されている最新の `update_date`** を比較します。

```php
private function isOrderUpdatedSinceFormRendered(FormInterface $form, Order $OriginOrder): bool
{
    $currentUpdateDate = $OriginOrder->getUpdateDate();
    if (null === $currentUpdateDate) {
        return false;
    }
    $renderedUpdateDate = $form->get('form_update_date')->getData();
    if (null === $renderedUpdateDate || '' === $renderedUpdateDate) {
        return false;
    }

    return $renderedUpdateDate !== $currentUpdateDate->format('Y-m-d H:i:s');
}
```

一致しなければ「別の操作で更新済み」と判断し、保存処理そのものを中断してエラーメッセージ(「受注情報が別の操作で更新されたため、登録できませんでした。画面を再読み込みしてからやり直してください。」)を表示します。これにより、1回目の送信で `update_date` が更新された後に届く2回目の送信は、DBを触る前の時点で弾かれます。

`$renderedUpdateDate` が空の場合はチェックをスキップする、という分岐がある点も見逃せません。これはプログラム的に(このフィールドを持たない形で)POSTを行う既存の外部連携やテストコードとの後方互換性を壊さないための配慮です。

### レイヤー2(クライアント側): フォーム単位の送信ガード

`function.js` には、Laddaのタイムアウトでボタンが再有効化された後の保険として、フォーム単位で二重送信を防ぐガードが追加されています。

```js
$('form').on('submit', function () {
    var $form = $(this);
    if ($form.data('ecSubmitted')) {
        return false;
    }
    $form.data('ecSubmitted', true);
});
```

こちらは「気の利いたユーザー体験の改善」であり、前述の通りXHRによる二重送信までは防げません。あくまでレイヤー1が本命で、レイヤー2は通常のブラウザ操作における体感を良くするための補助、という位置づけです。

## なぜ本格的な楽観的ロックにしなかったのか

ここがこのPRで一番興味深い設計判断です。レビューでは `coderabbitai`(AIレビューボット)から「これは `update_date` の単純比較であって、Doctrineの `#[Version]` を使った本来の楽観的ロックではないのでは」という指摘が入っています。

Doctrine公式ドキュメントが説明する楽観的ロックは、エンティティに `#[Version]` 属性を持つフィールド(整数を推奨)を持たせ、`flush()` 時にDB上のバージョンと比較して不一致なら `OptimisticLockException` を投げる、という仕組みです。これを導入すれば、更新日時の手動比較よりも堅牢な仕組みになります。

これに対して作者は、「今回のバグはDoctrineのスキーマ変更を伴わずに直せる、逐次的な(sequential)二重送信、つまり**1回目の送信がコミットされた後に2回目の送信が処理される**ケースに限定される」と説明しています。実際、`OrderItem` が破損するメカニズム自体が「2回目の送信が、1回目でDBに反映された後の状態に対して古いPOSTデータを適用する」という逐次実行を前提にしているため、この対策で再現ケースは解消します。

一方で、**2つのリクエストが完全に同時にDBを読みに行き、どちらもコミット前の状態を見ている**という真の競合(2つの管理者が同時に同じ受注を編集する等)は、このPRの対策では防げず、後勝ち(last-writer-wins)のままです。作者はこれを「通常の同時編集の挙動であり、`OrderItem` の破損には至らない」と整理し、スコープ外としています。レビュワーもこの説明に納得し、承認されています。

つまりこの修正は「完璧な排他制御」ではなく、「実際に報告された破損パターンをピンポイントで塞ぐ、スキーマ変更なしの現実的な対策」です。マイナーバージョンでの互換性維持(既存プラグイン・カスタマイズへの影響を避ける)を重視するEC-CUBEらしい判断と言えます。

## プラグイン開発者・カスタマイズ担当者への影響

自作の管理画面で、複数行の明細(受注明細、在庫、複雑なフォームコレクション等)を編集・保存する機能を持っている場合、同種の問題が起きていないか確認する価値があります。着目すべきポイントは次の通りです。

- **保存に時間がかかる編集画面はないか**。行数が多い、あるいは重い処理(在庫連携等)を伴う保存処理があると、ユーザーが「反応がない」と感じて再送信しやすくなります。
- **フォーム側で行の並べ替え・削除・追加を動的に行っていないか**。今回のバグの本質は「POSTのインデックスとDBの行が、処理タイミングによってずれる」ことです。単純なフィールド更新だけの画面であれば影響は軽微ですが、コレクション型のフォーム(明細行を増減できる画面)は同じ罠にはまりやすい構造です。
- **対策を入れるなら、EC-CUBE本体と同じ「隠しフィールドで描画時点のタイムスタンプを持たせ、保存時に照合する」パターンが手軽です**。スキーマ変更が不要な分、既存の管理画面に後から組み込みやすい対策です。より堅牢にしたい場合は、対象エンティティに `#[Version]` を追加した本格的な楽観的ロックも検討してください。

自分のプラグイン、複数行フォームの二重送信は本当に大丈夫だと言い切れますか。

## おまけ: あなたが実装者なら、どちらを選びますか

このPRの設計判断は、賛否が分かれてもおかしくないものだと思います。作者は「スキーマ変更を避け、報告された破損パターンをピンポイントに塞ぐ」ことを選び、レビュワーもそれに納得しました。一方で、真の同時編集競合(2人の管理者が同時に同じ受注を開く)は今回もlast-writer-winsのまま残っています。

もしあなたが実装者だったら、最初から `#[Version]` による本格的な楽観的ロックを入れる判断をしましたか。それとも、今回のように「実際に報告された壊れ方」に対象を絞った最小限の修正を選びますか。正解のない判断だからこそ、コメントで意見を聞いてみたいところです。

## まとめ

- 管理画面の受注編集で、保存ボタンの2秒タイムアウトが原因の二重送信により、受注明細データが破損する不具合が存在します。
- EC-CUBE 4.4で、隠しフィールドによる更新日時チェック(サーバー側・本命)とJSの二重送信ガード(クライアント側・補助)の二層で修正されます。
- CSRFトークンは二重送信対策にはならず、JS側のボタン無効化だけではXHR経由の二重送信を防げません。
- 本格的な楽観的ロック(Doctrineの`#[Version]`)ではなく更新日時比較を選んだのは、報告された破損パターン(逐次的な二重送信)をスキーマ変更なしでピンポイントに塞ぐための判断です。真の同時編集競合は今回のスコープ外として明示的に許容されています。

正式リリース時には実装が変わっている可能性があるため、最終的な仕様は公式のリリースノートや doc4.ec-cube.net でご確認ください。
