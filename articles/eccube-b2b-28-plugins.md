EC-CUBE で法人向けの案件を受けると、だいたい同じところで詰まります。卸価格、掛売り、1社に複数の発注担当者。標準の EC-CUBE はどれも持っていないので、毎回カスタマイズで作ることになります。

同じものを何度も作るくらいならプラグインにしたほうがいい、と思って作り始めたら28本になりました。紹介サイトを立てたので、この記事では中身の話をします。

https://b2b.eccube-plugin.net/

## 標準の EC-CUBE が想定していないこと

EC-CUBE は BtoC の買い方に合わせて作られています。会員はフラットで、価格は商品ごとに1つ、決済は受注1件ごと。この3つが、法人取引だとそのまま制約になります。

| 法人取引での前提 | EC-CUBE 標準 |
| --- | --- |
| 得意先ごとに単価が違う | 価格は商品に1つ |
| 1社に発注担当者が何人もいる | 会員はフラット。担当者ごとに別会員を作るしかない |
| 月末に締めてまとめて払う | 決済は受注1件ごと。掛売りにすると「未決済」の受注が溜まる |
| 発注には社内の決裁が要る | 注文はそのまま店舗へ流れる。止める場所がない |
| 取引先かどうか確かめてから受け入れたい | メールの URL を開いた時点で本会員 |

どれも運用でごまかせません。卸価格を出したいだけでも商品テーブルの外に価格を持つ必要があり、そこを作ると今度は「担当者全員に効かせたい」が来ます。

## 28本の内訳

土台になるものと、その上に載るアドオン、単体で動くものに分かれます。

### 会員まわりの土台（3本）

| プラグイン | 何をするか | 依存 |
| --- | --- | --- |
| 会員グループ管理 | 会員をグループに分け、商品・カテゴリ・ページの閲覧を出し分ける | 単体 |
| 取引先アカウント管理 | 会員に親子関係を持たせ、1社の下に担当者をぶら下げる | 単体 |
| 会員登録承認制 | 本会員化の URL を会員ではなく管理者へ送る | 単体 |

この3本が、ほかのプラグインの前提になります。

会員登録承認制は仕組みとしては単純で、本会員化の URL を会員宛てのメールから抜いて管理者宛てのメールに入れるだけです。会員は自分で本会員になれません。承認するまで仮会員なので、卸価格も見えません。

### 土台に載るアドオン（5本）

| プラグイン | 何をするか | 依存 |
| --- | --- | --- |
| 会員グループ価格管理 | グループごとに価格・掛け率・割引率・まとめ買いの値引きを設定 | 会員グループ管理 |
| 支払い方法管理 | グループごとに購入手続きの支払い方法を出し分け | 会員グループ管理 |
| 配送方法管理 | グループごとに購入手続きの配送方法を出し分け | 会員グループ管理 |
| 月締め請求管理 | 取引先ごとに受注をまとめ、締め日で1枚の請求にする | 取引先アカウント管理 |
| 発注承認 | 担当者の発注を承認待ちで止める | 取引先アカウント管理 |

支払い方法管理は、設定を2つに分けてあります。「利用可能な会員グループ」（支払い方法の側から絞る）と「このグループが使える支払い方法」（会員グループの側から絞る）で、両方を満たしたものだけが選べます。

1つにまとめなかったのは、言いたいことが2つあるからです。「請求書払いは法人だけ」にチェックを入れた瞬間に「法人は請求書払いだけ」も成立してしまうと、法人が銀行振込を使えなくなります。

### 注文のしかたを変えるもの（8本）

| プラグイン | 何をするか |
| --- | --- |
| 型番一括発注 | 型番と数量を貼り付けてまとめてカートに入れる。Excel からそのまま貼れる |
| 発注単位管理 | 発注単位と最低発注数を、カートと購入手続きの両方で守らせる |
| 色サイズ一括入力 | 色×サイズの表からまとめて数量を入れる |
| 切り売り・寸法指定 | 数量ではなく寸法で買う。刻みと上下限を決められる |
| 定期発注 | 決めた周期で発注の期日を知らせ、リンクからカートを作る |
| 予約・先行受注 | 発売前の商品を受け付け、発売日を過ぎたら通常販売に戻る |
| サンプル請求 | 生地やスワッチの請求を画面で受ける |
| 見積依頼 | カートの中身から見積を依頼し、承認された金額のまま注文にする |

型番一括発注は、いちばん相談の多かった機能です。毎月おなじ20品目を1品ずつ検索させるくらいなら、Excel から貼らせたほうが早い。

### 商品を探す・比べる（4本）

| プラグイン | 何をするか |
| --- | --- |
| 商品スペック検索 | 商品に規格の項目を持たせ、数値は範囲で絞り込む |
| 製品比較 | 選んだ商品を並べて比べる |
| 代替品・後継品提案 | 廃番・在庫切れの商品ページに代わりに買える商品を出す |
| 商品資料配布 | 図面・規格書・取扱説明書を商品ページから配布する |

商品資料配布は、ファイルを公開ディレクトリに置きません。公開範囲を見てからレスポンスとして返します。URL さえ知っていれば誰でも落とせる状態だと、会員限定の意味がなくなるためです。

### 出荷と書類（6本）

| プラグイン | 何をするか |
| --- | --- |
| 温度帯別配送 | 常温・冷蔵・冷凍を別の便に分け、便ごとにクール料金を足す。注文は1件のまま |
| 納品場所指定 | お届け先に搬入の手引きと写真を付ける |
| 部屋分け発注 | 1回の発注を病室・ユニット・部署ごとに配り分ける。お届け先は分けない |
| 不定貫商品 | 重さで代金が決まる商品を、目安の金額で受けて出荷前の計量で確定する |
| 注文請書・発注書 | 注文から注文請書と発注書の PDF を出す |
| 案件別注文管理 | 注文に案件名・工番を持たせ、受注一覧で絞り込む |

納品場所指定は、注文時点の搬入手引きを文字として注文にコピーします。お届け先のマスタを参照するだけだと、あとから手引きを直したときに過去の出荷指示まで変わってしまうためです。

### 見せる相手を絞る（2本）

| プラグイン | 何をするか |
| --- | --- |
| 会員限定サイト | サイト全体を会員限定にし、未ログインの人はログインページへ回す |
| 購入資格 | 店が確認して承認した資格を持つ会員にだけ売る |

購入資格は医療機器や医薬品のように、法令で売り先が決まっている商材向けです。

## 全部入れる必要はない

28本を並べましたが、全部入れる構成は想定していません。どこまで要るかは商習慣で変わります。

| 構成 | 本数 | 入れるもの |
| --- | --- | --- |
| 卸価格だけ | 2本 | 会員グループ管理 → 会員グループ価格管理 |
| 法人サイト標準 | 6本 | 上記＋支払い方法管理／配送方法管理／会員登録承認制／型番一括発注 |
| 掛売り・稟議つき | 9本 | 上記＋取引先アカウント管理／月締め請求管理／発注承認 |

アドオンは土台が有効になっていないと有効化できないので、順序があります。会員グループ価格管理より先に会員グループ管理を、月締め請求管理より先に取引先アカウント管理を入れます。

色×サイズや温度帯のような商材で決まる部分は、この土台の上に必要なものだけ足します。どれも単体で動くので順序はありません。

## 商習慣に合わない部分をどうするか

ここからが本題です。

法人向けの機能は、どこまで作り込んでも会社ごとの差が残ります。締め日が20日の会社、請求番号を会計システムの採番に合わせたい会社、支払期日が休業日なら翌営業日にずらす会社。設定項目をいくら増やしても足りません。

そこで、主要な処理をインターフェースとして切り出しました。22本のプラグインに、あわせて31か所あります。

### 差し替え口の例

月締め請求管理だけで8か所あります。

| インターフェース | できること |
| --- | --- |
| `BillableOrderCriteriaInterface` | 締め対象の受注の絞り込みを足す |
| `BillingPartyResolverInterface` | 請求先の決め方を変える（部署単位の請求など） |
| `InvoiceNumberGeneratorInterface` | 請求番号の採り方を会計システムに合わせる |
| `DueDateResolverInterface` | 支払期日をずらす |
| `TaxSummarizerInterface` | 消費税の計算方法を足す |
| `ReturnCollectorInterface` | 外部の返品管理から返還を取り込む |
| `InvoiceDocumentInterface` | 帳票の種類を足す |
| `PaymentRestrictionInterface` | 支払方法を会員ごとに絞る |

ほかにも、型番一括発注には貼られた文字列を自社の型番へ読み替える `ProductCodeTranslatorInterface`、発注承認には承認者の決め方を変える `ApproverResolverInterface`、不定貫商品には端数の扱いを差し替える `WeightPricingInterface` があります。

### 置くだけで登録される

実装の置き場所は EC-CUBE 標準のカスタマイズ領域、`app/Customize` です。インターフェースを実装したクラスを置けば、それだけでプラグインから呼ばれます。`services.yaml` に書き足す作業はありません。

```php
namespace Customize\B2BBilling;

use Plugin\B2BBilling\Service\Billing\DueDate\DueDateResolverInterface;

class BusinessDayDueDateResolver implements DueDateResolverInterface
{
    public function resolve(?\DateTimeImmutable $current, BillingContext $context): ?\DateTimeImmutable
    {
        // 前の実装が出した支払期日を受け取り、休業日なら翌営業日へずらして返す
    }
}
```

順番を変えたいときだけ、クラスに1行足します。

```php
use Symfony\Component\DependencyInjection\Attribute\AsTaggedItem;

#[AsTaggedItem(priority: 50)]
class PublishDateGuard implements VisibilityGuardInterface
```

`priority` を指定しなければ 0 として扱われ、既定の実装と同じ列に並びます。上げると先に呼ばれます。

### 束ね方は4種類

複数の実装をどう束ねるかは、差し替え口ごとに決めてあります。ここを取り違えると、書いたのに効かない、あるいは効きすぎることになります。

| 束ね方 | どうなるか | 例 |
| --- | --- | --- |
| 全部呼ぶ（AND） | 1つでも止めれば止まる。足した判定で既定を緩められない | `VisibilityGuardInterface` |
| 先に決めた1本が勝つ | 優先度の高い順に呼び、最初に答えた実装を使う | `PriceResolverInterface` |
| 前の結果を受け取る | 前の実装が出した値を加工して返す | `DueDateResolverInterface` |
| 結果を連結する | 全実装の結果をつなげて使う | `ReturnCollectorInterface` |

見せるかどうかや売っていいかどうかの判定は、意図的に AND にしてあります。あとから足した実装で既定の制限を緩められると、うっかり書いた1本で卸価格が全員に見えます。購入資格の `PurchasePermissionInterface` とサンプル請求の `SampleEligibilityInterface` も、絞る方向にしか働きません。

価格や承認者のように答えが1つに決まるものは、優先度順に見て最初に名乗り出た実装を使います。決められないときは次へ譲ります。

## AI に書かせることを前提にした

差し替え口を切ったのは、AI コーディングツールに書かせるためでもあります。

書く場所が1クラスに決まっていて、置けば登録されて、束ね方も決まっている。この形なら「よしなにやっといて」の丸投げになりません。各プラグインには `CLAUDE.md` と `docs/extension-samples.md` を同梱していて、差し替え口ごとにコピーして使えるサンプルが入っています。

頼み方はこうなります。

```
app/Plugin/B2BBilling/docs/extension-samples.md を読んで、
支払期日が土日祝なら翌営業日にずらす DueDateResolverInterface の実装を
app/Customize に追加してください。休業日は自前のテーブルから引きます。
```

出てくるのは上に載せたクラス1つです。プラグイン本体も EC-CUBE 本体も1行も変わりません。本体を書き換えると、次の版が出るたびに当て直すことになります。

ただし、AI が書いたコードをそのまま本番に入れないでください。動いて見えても条件の取り違えが混ざります。請求と在庫にかかわる部分は金額がずれても気づきにくいので、テスト環境で締めを1回通して、出てきた請求書を目で確かめてから入れます。手引きには確かめる手順も書いてあるので、そこまで AI にやらせるのが早いです。

差し替え口が無いところは、AI でも足せません。そこはプラグイン本体を書き換えることになるので、こちらで引き受けます。

## 業種で分かれるところ

卸価格と掛売りはどの業種にも共通しますが、そこから先は商習慣で分かれます。プラグインが名指しで想定しているのは次の6つです。

| 業種 | 組み合わせ |
| --- | --- |
| アパレル・繊維 | 商品スペック検索／色サイズ一括入力／切り売り・寸法指定／予約・先行受注／サンプル請求 |
| 食品 | 商品資料配布／温度帯別配送／不定貫商品 |
| 建設・電材 | 代替品・後継品提案／案件別注文管理／納品場所指定 |
| 医療・福祉 | 購入資格／定期発注／部屋分け発注 |
| 鋼材・電子部品 | 商品スペック検索／製品比較／代替品・後継品提案／切り売り・寸法指定 |
| 機械・工業用品 | 製品比較／商品資料配布／定期発注 |

食品の温度帯別配送は、注文を分けずに出荷だけ分けます。注文を分けてしまうと、送料も請求も会員から見た履歴も全部2件になります。医療・福祉の部屋分け発注も同じ考え方で、荷物は施設に1つ届き、中でどう配るかだけを持ちます。

## 価格

プラグインは一律1本6万円（税別・予定価格）の買い切りです。月額はありません。値段が全部同じなので、本数を数えれば総額が出ます。

| 費目 | 金額 |
| --- | --- |
| EC-CUBE 本体 | 0円（LGPL） |
| プラグイン | 1本6万円（税別・予定価格） |
| 構築 | 個別見積り |
| サーバー | VPS 1台の月額。2〜4GB が目安 |

構成でいうと、卸価格だけなら12万円、法人サイト標準で36万円、掛売り・稟議つきで54万円です。

B2B 向けの EC パッケージや SaaS は、初期費用に加えて月額がかかるのが普通です。この構成で毎月かかるのはサーバー代だけで、取引が増えても月額は上がりません。

そのぶん、パッケージのように全部入りですぐ動くわけではありません。どこまで必要かを決めて、選んで組む手間はかかります。

## おわりに

法人向けの EC は、機能が何本あるかより、その店の商習慣に寄せられるかで決まります。締め日も請求番号も承認のラインも、会社ごとに違うものを設定項目で全部吸収するのは無理です。

なので、合わない前提で作りました。設定で足りるところは設定で、足りないところは差し替え口で、口の無いところは作り足しで。差し替え口を31か所に切って手引きを同梱したのは、その真ん中の層を AI に任せられるようにするためです。
