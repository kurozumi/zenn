## 結論: 「英数字を混ぜてください」が消えて、15文字必須になります

EC-CUBE 4.4 で、パスワードの要件が NIST SP 800-63B-4 に沿った内容へ変わります（[PR #6858](https://github.com/EC-CUBE/ec-cube/pull/6858)、`4.4` ブランチに 2026年7月8日マージ済み、+1,248/-178）。

変更の方向は、直感と逆かもしれません。

| 項目 | 4.3 | 4.4 |
| --- | --- | --- |
| 最小文字数 | 12 | **15** |
| 最大文字数 | 50 | **128** |
| 文字種の要件 | 英字と数字を各1文字以上 | **撤廃**（全 Unicode を許可） |
| 漏洩チェック | なし | **既定ON**（HaveIBeenPwned） |
| ブロックリスト | なし | 同梱（差し替え可） |

**複雑さの要件を捨てて、長さと漏洩実績で守る。** これが NIST SP 800-63B の考え方です。

**TL;DR**

- 最小15文字・最大128文字。`eccube_password_min_len` / `_max_len` で設定（[PR #6858](https://github.com/EC-CUBE/ec-cube/pull/6858)）
- 「英字＋数字」の複雑さ要件を撤廃し、絵文字や日本語も使えるように
- 制御文字・不可視文字（`\pC`）だけ拒否
- Symfony 標準の `NotCompromisedPassword` で HaveIBeenPwned 照合。**既定ON**
- API 到達不可でも登録は継続（`skipOnError: true`）。閉域網では設定で無効化できる
- 「15文字以上だが弱い」パターンに絞った小さなブロックリストを同梱
- パスワードハッシャーは変更なし（バリデーション層のみの対応）

## なぜ「複雑さ」をやめるのか

`Passw0rd!` を見てください。大文字・小文字・数字・記号をすべて含み、たいていのバリデーションを通ります。そして攻撃者の辞書にも載っています。

複雑さの要件は、人間に**予測可能な変形**を強います。`a` を `@` に、`o` を `0` に、末尾に `1!` を足す。要件を満たす最短経路が決まっているので、結果として似たパスワードが量産されます。

NIST SP 800-63B-4 が推奨するのは、複雑さの強制をやめて長さを確保し、既知の漏洩パスワードを拒否することです。EC-CUBE 4.4 の変更はこれをそのまま実装したものです。

## 設定値の変更

`app/config/eccube/packages/eccube.yaml` を見ると、こうなっています。

```yaml
    eccube_password_min_len: 15
    eccube_password_max_len: 128
    eccube_password_pattern: '/\A[\pL\pM\pN\pP\pS\pZ]+\z/u'
    eccube_password_compromised_check: true
    eccube_password_blocklist: '%kernel.project_dir%/src/Eccube/Resource/password_blocklist.txt'
```

### 正規表現が変わりました

4.3 のパターンはこうでした。

```
/\A(?=.*?[a-z])(?=.*?\d)[!-~]+\z/i
```

先読みで「英字が1つ以上」「数字が1つ以上」を強制し、使える文字を ASCII の印字可能文字（`!-~`）に限定しています。

4.4 はこうです。

```
/\A[\pL\pM\pN\pP\pS\pZ]+\z/u
```

Unicode の一般カテゴリで許可する文字を指定しています。

| カテゴリ | 内容 |
| --- | --- |
| `\pL` | 文字（Letter）。英字だけでなく、ひらがな・漢字・キリル文字など |
| `\pM` | 結合文字（Mark） |
| `\pN` | 数字（Number） |
| `\pP` | 約物（Punctuation） |
| `\pS` | 記号（Symbol）。絵文字を含む |
| `\pZ` | 区切り（Separator）。スペースなど |

先読みがないので**文字種の強制はありません**。残る `\pC`（制御文字や書式文字、未割り当て）だけを弾きます。

つまり `パスワードは長いほうがいい` のような日本語のパスフレーズも、絵文字混じりも通ります。**スペースも使えます**（`\pZ`）。パスフレーズを使いたい人には重要な点です。

:::message
最小15文字は英語圏では「単語3〜4個のパスフレーズ」を想定した長さです。日本語話者にとっては、ローマ字入力で15文字はやや長く感じるかもしれません。ただし日本語のまま入力できるので、`私の猫の名前はタマです` のような入力も可能になりました。
:::

## 漏洩チェック（HaveIBeenPwned）

Symfony 標準の `NotCompromisedPassword` 制約が、全パスワードフォームに適用されます。

```php
$constraints[] = new Assert\NotCompromisedPassword(['skipOnError' => true]);
```

この制約は HaveIBeenPwned の Pwned Passwords API に問い合わせて、そのパスワードが既知の漏洩リストに含まれるかを判定します。

**パスワードそのものは送信されません。** k-Anonymity という方式で、SHA-1 ハッシュの先頭5文字だけを送り、該当する候補群を受け取ってローカルで突き合わせます。API 提供側にも完全なハッシュは渡りません。

### `skipOnError: true` の意味

ここが実運用で効きます。`skipOnError` を `true` にすると、**API に到達できなかった場合はチェックをスキップして通す**動作になります。

外部 API への依存を検証に組み込むと、API 障害やネットワーク断で会員登録ができなくなります。それを避けるための設定です。

セキュリティとしては「弱くなる方向にフェイルする」選択なので、賛否はあると思います。ただし EC サイトで会員登録が丸ごと止まるほうが事業影響は大きい、という判断は理解できます。

### 閉域網では切ってください

社内ネットワークやオフライン環境では、そもそも API に到達できません。毎回タイムアウトを待つことになるので、明示的に無効化します。

```yaml
    eccube_password_compromised_check: false
```

外部への通信が発生することを把握しておくのも大事です。**要件で外部通信が禁止されている案件では、この設定を必ず確認してください。** 既定が `true` なので、何もしなければ通信します。

依存として `symfony/http-client` が追加されています。

## ブロックリスト

漏洩チェックとは別に、小さなブロックリストが同梱されています。

```
src/Eccube/Resource/password_blocklist.txt
```

ファイル冒頭のコメントに、狙いが書かれています。

```
# NIST SP 800-63B-4 に基づき, 推測されやすいパスワードを拒否するためのリストです.
# eccube_password_min_len(既定15)以上の長さがあっても弱いパターンに絞って収録しています.
# 網羅的な漏洩チェックは HaveIBeenPwned(NotCompromisedPassword)に委ねます.
```

**網羅性を狙っていません。** 「15文字以上あるのに弱い」古典的なパターンだけを収録した、67行ほどの小さなリストです。網羅は HaveIBeenPwned の仕事、という役割分担になっています。

照合処理は `PasswordBlocklistValidator` にあります。

```php
/**
 * 比較用に NFKC 正規化し小文字化する.
 */
private function normalizeForComparison(string $value): string
{
    return mb_strtolower((string) PasswordNormalizer::normalize($value));
}
```

NFKC 正規化してから小文字化して突き合わせます。全角英数字で入力しても半角と同じ扱いになるので、`ｐａｓｓｗｏｒｄ１２３４５６７` のような回避ができません。日本語環境では地味に効く処理です。

### 差し替えられます

`eccube_password_blocklist` はパスの設定なので、自社のリストに差し替えられます。

```yaml
    eccube_password_blocklist: '%kernel.project_dir%/app/Customize/Resource/my_blocklist.txt'
```

店舗名やブランド名を含むパスワードを弾きたい場合に使えます。`yourshop2026pass` のようなパターンは HaveIBeenPwned には載りませんが、その店舗にとっては弱いパスワードです。

## ハッシャーは変えていません

重要な線引きとして、**パスワードハッシャーは変更されていません**。

Issue #6488 で決められた方針が「バリデーション層のみで対応・ハッシャー `auto` は変更しない」でした。既存会員のパスワードハッシュはそのまま使えます。マイグレーションは不要です。

これは移行の負担を考えると妥当な判断です。ハッシュ方式を変えると全員に再設定を強いるか、ログイン時の再ハッシュを仕込む必要があります。

## 既存会員はどうなるか

バリデーションは**新しくパスワードを設定するとき**に走ります。既存会員が 12文字のパスワードのままログインすることは引き続きできます。

影響が出るのは次のタイミングです。

- 新規会員登録
- 会員によるパスワード変更
- パスワード再発行
- 管理画面からのメンバー登録・パスワード変更

つまり**移行時に既存会員が締め出されることはありません**。ただしパスワード変更しようとした会員が「15文字必要です」と言われて戸惑う可能性はあります。フロントのメッセージや案内を確認しておくとよいでしょう。

## カスタマイズしている場合の確認点

パスワード関連をいじっているなら、次を見ておくと安全です。

**独自のパスワードフォームを持っている場合。** `RepeatedPasswordType` を使わずに自前で組んでいると、4.4 の制約は自動では付きません。`NotCompromisedPassword` やブロックリスト検証を自分で足す必要があります。

**バリデーションメッセージを上書きしている場合。** 文字種の要件が消えたので、「英数字を組み合わせてください」というメッセージが実態と合わなくなります。翻訳ファイルを上書きしているなら見直してください。

**最大長を DB 側で制限している場合。** 最大128文字になりました。パスワードはハッシュ化されて保存されるのでカラム長には影響しませんが、フロント側の `maxlength` 属性を独自に設定しているテンプレートがあれば直す必要があります。

**入力欄のプレースホルダやヘルプテキスト。** 「半角英数字12文字以上」のような案内が残っていると、そのままでは誤案内になります。

## まとめ

- EC-CUBE 4.4 のパスワード要件が NIST SP 800-63B-4 準拠に（[PR #6858](https://github.com/EC-CUBE/ec-cube/pull/6858)）
- 最小15文字・最大128文字。文字種の複雑さ要件は撤廃され、日本語・絵文字・スペースも使える
- 制御文字（`\pC`）だけ拒否する `/\A[\pL\pM\pN\pP\pS\pZ]+\z/u` に変更
- HaveIBeenPwned による漏洩チェックが既定ON。**外部通信が発生する点に注意**。閉域網では `eccube_password_compromised_check: false`
- ブロックリストは網羅目的ではなく「長いのに弱い」パターン用。NFKC 正規化して照合するので全角回避が効かない
- ハッシャーは変更なし。既存会員のログインには影響しない

「記号を混ぜてください」という要件は、長らくセキュリティの常識でした。それが推奨されなくなった理由まで含めて、実装で示されたのが今回の変更です。自社サービスのパスワードポリシーを見直すきっかけにもなると思います。
