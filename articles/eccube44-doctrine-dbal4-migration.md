## 結論: `$conn->query()` を書いているプラグインは、4.4で全部死にます

EC-CUBE 4.4 で Doctrine DBAL が **3.10 系から 4.4** へ上がります（[PR #6855](https://github.com/EC-CUBE/ec-cube/pull/6855)、`4.4` ブランチに 2026年7月16日マージ済み、+513/-435・49ファイル）。

DBAL 4 は Doctrine の中でも特に容赦のないメジャーアップで、**よく使うメソッドが軒並み削除されています**。プラグインで生 SQL を投げている方は、まず以下を `grep` してください。1つでも引っかかったら 4.4 では動きません。

```bash
grep -rnE -e '->(query|exec|executeUpdate|fetch|fetchAll|getSchemaManager|listTableDetails|getWrappedConnection)\(' app/Plugin/
```

（パターンが `-` で始まるので `-e` が必要です。付け忘れると grep がオプションとして解釈してエラーになります）

そしてもう1つ、コードを直しただけでは済まない話があります。**PostgreSQL を使っている環境では、自動採番列が `SERIAL` から `IDENTITY` に変わります。** これは DBAL 側の仕様変更で、EC-CUBE 側から止める手段はありません。

**TL;DR**

- `doctrine/dbal` が 4.3 の `^3.3` から 4.4 では `^4.4` に（[PR #6855](https://github.com/EC-CUBE/ec-cube/pull/6855) が `^3.8` → `^4.4` を実施）。`doctrine/cache` は依存から削除
- `Connection::query()` / `exec()` / `executeUpdate()` / `Result::fetch()` / `fetchAll()` / `getSchemaManager()` などが **削除済み**
- `AbstractPlatform::getName()` が消えたので、DB 種別判定は `instanceof` に書き換えが必要
- **PostgreSQL: 自動採番列が `SERIAL` → `GENERATED BY DEFAULT AS IDENTITY` に変わる**（DBAL の BC BREAK、回避オプションなし）
- **MySQL: `lastInsertId()` が `'0'` のとき `NoIdentityValue` 例外を投げる**ようになった
- `DriverManager::getConnection()` が `url` パラメータを解析しなくなった（`DsnParser` で展開が必要）
- `postConnect` イベントは廃止。接続時の初期化 SQL は **Driver Middleware** で書く

## DB 種別の判定と `getName()` の削除

DBAL 3 まで、接続先が MySQL か PostgreSQL かを見る定番はこれでした。

```php
// DBAL 3 まで
$platform = $conn->getDatabasePlatform()->getName();
if ($platform === 'mysql') {
    // ...
}
```

DBAL 4 で `AbstractPlatform::getName()` は削除されました。EC-CUBE 4.4 では `instanceof` による判定に統一されています。

```php
use Doctrine\DBAL\Platforms\AbstractMySQLPlatform;

if ($conn->getDatabasePlatform() instanceof AbstractMySQLPlatform) {
    // MySQL / MariaDB
}
```

ここで重要なのが、具象の `MySQLPlatform` ではなく抽象の `AbstractMySQLPlatform` で判定している点です。

DBAL 4 の継承関係はこうなっています。

```
AbstractMySQLPlatform
├── MySQLPlatform
│   └── MySQL80Platform
│       └── MySQL84Platform
└── MariaDBPlatform
```

`MariaDBPlatform` は `MySQLPlatform` を継承せず、`AbstractMySQLPlatform` を直接継承します。つまり `instanceof MySQLPlatform` で判定すると **MariaDB だけ判定が外れます**（MySQL 8 / 8.4 は `MySQLPlatform` を継承しているので拾えます）。MariaDB を落とさないために、抽象側で見るのが安全です。

PostgreSQL は `PostgreSQLPlatform`、SQLite は `SQLitePlatform` です。DBAL 3 の `SqlitePlatform` から綴りが変わっているので、そのまま置換すると見つかりません。

## 削除されたAPIの対応表

PR #6855 で一括置換された内容をまとめます。プラグインの書き換え表としてそのまま使えます。

| DBAL 4 で使えなくなった API | DBAL 4 での書き方 |
| --- | --- |
| `AbstractPlatform::getName()` | `instanceof AbstractMySQLPlatform` など |
| `Connection::query()` | `Connection::executeQuery()` |
| `Connection::exec()` | `Connection::executeStatement()` |
| `Connection::executeUpdate()` | `Connection::executeStatement()` |
| `Statement::execute()` | private 化。`executeStatement()` / `executeQuery()` へ |
| `Result::fetch()` | `fetchAssociative()` / `fetchNumeric()` / `fetchOne()` |
| `Result::fetchAll()` | `fetchAllAssociative()` / `fetchAllNumeric()` |
| `Connection::getSchemaManager()` | `Connection::createSchemaManager()` |
| `AbstractSchemaManager::listTableDetails()` | `introspectTable()`（下記の注意あり） |
| `Table::hasPrimaryKey()` | 廃止（`getPrimaryKey()` の null 判定へ） |
| `Connection::getWrappedConnection()` | 廃止（`getNativeConnection()` を検討） |
| `Statement::bindParam()` | 廃止（`bindValue()` へ） |
| `AbstractPlatform::markDoctrineTypeCommented()` / `Type::requiresSQLCommentHint()` | 廃止（コメントヒント機構ごと撤廃） |
| `Configuration::setSQLLogger()` | 廃止（Middleware / Logging へ） |
| DBAL `QueryBuilder::execute()` | `executeQuery()` / `executeStatement()` |

`Connection::connect()` も protected 化されたので、外から `$conn->connect()` を呼んでいるコードがあれば動きません。

2点、補足しておきます。

`fetch()` / `fetchAll()` は `Statement` ではなく `Result` のメソッドです（`Statement::fetch()` は DBAL 3 の時点ですでに削除済みなので、それを呼んでいるコードは 4.3 でも動きません）。

そして `introspectTable()` は、**EC-CUBE 4.4 が要求する DBAL 4.4 の時点ですでに非推奨です**。UPGRADE.md の「Upgrade to 4.4」節で `introspectTableByUnquotedName()` / `introspectTableByQuotedName()` への移行が案内されています（`listTableNames()` / `listTableColumns()` / `listTables()` も同様）。いま書き換えるなら、`introspectTable()` を経由せず新しい API に直接寄せたほうが手戻りがありません。

## 接続時の初期化は Driver Middleware へ

EC-CUBE は接続確立時に初期化 SQL を流しています。MySQL ならセッションのタイムゾーンを UTC に、PostgreSQL なら `SET TIME ZONE 'UTC'`。4.3 まではこれを `postConnect` イベントで実装していました。

```php
// 4.3: src/Eccube/Doctrine/EventSubscriber/InitSubscriber.php
class InitSubscriber implements EventSubscriber
{
    public function getSubscribedEvents()
    {
        return [Events::postConnect];
    }

    public function postConnect(ConnectionEventArgs $args)
    {
        $db = $args->getConnection();
        $platform = $args->getConnection()->getDatabasePlatform()->getName();

        if ($platform === 'mysql') {
            $db->executeQuery("SET SESSION time_zone = '+00:00'");
        } elseif ($platform === 'postgresql') {
            $db->executeQuery("SET TIME ZONE 'UTC'");
        } elseif ($platform === 'sqlite') {
            // FIXME schema updateが通らないので一旦コメントアウト.
            // $db->executeQuery("PRAGMA foreign_keys = ON");
        }
    }
}
```

DBAL 4 でイベントシステム自体が撤廃されたため、`postConnect` は使えません。4.4 では **Driver Middleware パターン** に書き換わっています。

```php
// 4.4: src/Eccube/Doctrine/EventSubscriber/InitSubscriber.php
use Doctrine\DBAL\Driver;
use Doctrine\DBAL\Driver\Middleware;

class InitSubscriber implements Middleware
{
    public function wrap(Driver $driver): Driver
    {
        return new InitDriver($driver);
    }
}
```

```php
// 4.4: src/Eccube/Doctrine/EventSubscriber/InitDriver.php
use Doctrine\DBAL\Driver\Connection as DriverConnection;
use Doctrine\DBAL\Driver\Middleware\AbstractDriverMiddleware;

class InitDriver extends AbstractDriverMiddleware
{
    #[\Override]
    public function connect(#[\SensitiveParameter] array $params): DriverConnection
    {
        $connection = parent::connect($params);

        $driver = (string) ($params['driver'] ?? '');
        if (str_contains($driver, 'mysql')) {
            $connection->exec("SET SESSION time_zone = '+00:00'");
        } elseif (str_contains($driver, 'pgsql') || str_contains($driver, 'postgres')) {
            $connection->exec("SET TIME ZONE 'UTC'");
        }
        // sqlite は schema update が通らないため PRAGMA foreign_keys は設定しない (従来踏襲)

        return $connection;
    }
}
```

DB 種別の判定が `$params['driver']` の文字列を見る形になっているのに注目してください。この時点ではまだ DBAL の `Connection`（＝`getDatabasePlatform()` を持つラッパー）ではなく生の Driver Connection なので、プラットフォームオブジェクトが取れません。

:::message
なお [#6686](https://github.com/EC-CUBE/ec-cube/pull/6686)（別途提出されていた Symfony 7 対応 PR）では `AbstractDriverMiddleware::wrappedDriver` という private プロパティをリフレクションで読む実装が採られていましたが、#6855 は「Doctrine の内部実装に依存して脆い」として採用せず、`$params['driver']` からの判定に変更しています。
:::

DI での登録はこうです（`app/config/eccube/services.yaml`）。

```yaml
    Eccube\Doctrine\EventSubscriber\InitSubscriber:
        autoconfigure: false
        tags:
            # 初期化 SQL (SET TIME ZONE 等) は物理接続へ 1 回だけ発行したいので,
            # dama/doctrine-test-bundle の StaticDriver (priority: 100) より内側 (実ドライバ直上) に
            # 配置する (DBAL 3 の postConnect イベント相当の挙動)。priority が高いほど内側になる。
            - { name: doctrine.middleware, priority: 200 }

    Eccube\Doctrine\EventSubscriber\InitDriver:
        autowire: false
        autoconfigure: false
```

Middleware は `priority` が高いほど実ドライバに近い（内側）という並びになります。DoctrineBundle の `MiddlewaresPass` が priority 降順にソートし、`DriverManager` が配列順に `$driver = $middleware->wrap($driver)` で包んでいくためです。テスト用の `StaticDriver`（priority 100）より内側に置くことで、テスト時も物理接続に1回だけ初期化 SQL が飛ぶようにしています。

ラップされる側の `InitDriver` を `autowire: false` で登録しておく点も忘れずに。プラグインで独自の Middleware を差し込むときは、この登録がそのまま雛形になります。

## キャッシュ設定と `DoctrineProvider` の廃止

DBAL 4 では `doctrine/cache` への依存自体がなくなり、`Doctrine\Common\Cache\Psr6\DoctrineProvider`（PSR-6 プールを旧 Doctrine Cache インターフェースに変換するアダプタ）も使えません。

4.3 の `app/config/eccube/packages/prod/doctrine.yaml` はこうでした。

```yaml
doctrine:
    orm:
        metadata_cache_driver:
            type: service
            id: doctrine.app_cache_provider
        # ...

services:
    doctrine.app_cache_provider:
        class: Doctrine\Common\Cache\Psr6\DoctrineProvider
        factory: ['Doctrine\Common\Cache\Psr6\DoctrineProvider', wrap]
        public: false
        arguments:
            - '@doctrine.app_cache_pool'
```

4.4 では PSR-6 プール直結になり、変換サービスごと消えました。

```yaml
doctrine:
    orm:
        metadata_cache_driver:
            type: pool
            pool: doctrine.app_cache_pool
        query_cache_driver:
            type: pool
            pool: doctrine.app_cache_pool
        result_cache_driver:
            type: pool
            pool: doctrine.app_cache_pool
        second_level_cache:
            region_cache_driver:
                type: pool
                pool: doctrine.app_cache_pool
```

プラグインで独自の doctrine キャッシュ設定を持っている場合、`type: service` からの書き換えが必要です。

## ⚠️ PostgreSQL: `SERIAL` が `IDENTITY` になる

ここからが本番です。**DBAL 4 では PostgreSQL の自動採番列が `SERIAL*` ではなく `GENERATED BY DEFAULT AS IDENTITY` で生成されます。** DBAL の `UPGRADE.md` に *"Auto-increment columns on PostgreSQL are implemented as `IDENTITY`, not `SERIAL`"* として記載されている変更で、**SERIAL を維持する設定オプションはありません**。

実務上、影響が出るのは次の2点です。

### 既存DBの採番が 1 に戻る問題

すでに稼働している本番 DB のカラムは `SERIAL` のままです。ここで軽く考えてはいけません。DBAL 公式の移行ガイド（[postgresql-identity-migration](https://github.com/doctrine/dbal/blob/4.4.x/docs/en/how-to/postgresql-identity-migration.rst)）は、こう警告しています。

> Without this migration, next time when DBAL 4 is used to manage the schema, it will perform a similar migration but instead of reusing the existing sequence, it will **drop it and create a new one. As a result, all new sequence numbers will be generated from `1`**, which is most likely undesired.

つまり手動移行をせずにスキーマ管理を DBAL 4 に任せると、**既存シーケンスが破棄されて新しいシーケンスが作られ、採番が 1 から再スタート**します。既存レコードと主キーが衝突します。

公式ガイドは、これを避けるための `upgrade_serial_to_identity()` という PL/pgSQL 関数を提示しています。ただしこの関数は `pg_depend` / `pg_attribute` というシステムカタログを直接書き換えるため、**PostgreSQL の superuser 権限が必要**です。AWS RDS・Cloud SQL・Azure Database・Supabase・Neon といったマネージドサービスでは superuser を取れないので、そのままでは実行できません。

EC-CUBE を PostgreSQL のマネージドサービスで運用している場合、4.4 へのアップグレードはこの一点だけで計画が変わります。移行手順を事前に設計してください。

:::message alert
本番環境で `doctrine:schema:update --force` をいきなり実行しないでください。

- 必ず `--dump-sql` で生成 SQL を目視し、バックアップを取得してから実行する
- `SERIAL` → `IDENTITY` の `ALTER` は大きなテーブルで排他ロックを取り、その間そのテーブルへの書き込みが止まる
- `schema:update` は列削除など**データを失う DDL** も生成します。差分を鵜呑みにしない
- 本番では `schema:update` ではなく、生成 SQL をレビューしたマイグレーション（`doctrine:migrations`）として流すのが安全です

これは 4.4 に限らず常に守るべき運用です。
:::

### シーケンス名が取れなくなる

`IDENTITY` の内部シーケンスは `information_schema.sequences` に現れません。従来のやり方、つまり `テーブル名_pk_seq` という命名規則を組み立てて `information_schema` を検索する方法では、シーケンス名を取得できなくなります。

EC-CUBE 側では実際にこれで踏み抜いていて、`CsvFixture` のシーケンス振り直しが黙ってスキップされ、`fixtures:load` 後もシーケンスが初期値のまま残り、テストで作るレコードの id が既存 fixture と衝突していたそうです。4.4 では `pg_get_serial_sequence()`（SERIAL / IDENTITY 両対応）でシーケンス名を取る実装に修正されています。

プラグインでシーケンス名を組み立てているコードがあれば、同じ罠にハマります。書き換えるときは、こう書いてください。

```php
// テーブル名は識別子なのでプレースホルダに直接は使えない。
// pg_get_serial_sequence() は識別子を「文字列引数」として受け取るので、
// バインドパラメータで安全に渡せる。
$seq = $conn->fetchOne(
    'SELECT pg_get_serial_sequence(?, ?)',
    [$tableName, $columnName]
);
```

テーブル名を SQL 文字列に直接埋め込むと、値の出どころ次第でそのまま SQL インジェクションになります。`pg_get_serial_sequence()` は識別子を文字列の引数として受け取る関数なので、バインドパラメータで渡せます。

## ⚠️ MySQL: `lastInsertId()` が `'0'` で例外を投げる

DBAL 4 では `Connection::lastInsertId()` が `'0'` を返す状況で `NoIdentityValue` 例外を投げるようになりました。DBAL 3 は単に `0` を返すだけでした。返り値が 0 なら採番されていない、という前提で書いたコードは、4.4 では**例外で落ちます**。

DBAL 4 の `src/Driver/PDO/Connection.php` の該当箇所はこうです。

```php
// pdo_mysql & pdo_sqlite return '0', pdo_sqlsrv returns '' or false depending on the PHP version
if ($value === '0' || $value === '' || $value === false) {
    throw NoIdentityValue::new();
}
```

catch するときに注意が必要です。ドライバ層で投げられるのは `Doctrine\DBAL\Driver\Exception\NoIdentityValue` ですが、これは `@internal` マーク付きで、ラッパーの `Doctrine\DBAL\Connection::lastInsertId()` を通ると `Doctrine\DBAL\Exception\DriverException` に変換されて上がってきます。アプリ側で捕まえるなら後者です。

EC-CUBE 側では、テスト用フィクスチャ生成（`tests/Eccube/Tests/Fixture/Generator.php`）のバルク INSERT でこれを踏んでおり、MySQL では `SELECT LAST_INSERT_ID()` で採番値を取得するよう修正されています。本体コードではなくテストコードでの対応ですが、ネイティブ prepared statement でバルク INSERT を書いているプラグインには、そのまま当てはまる話です。

なお SQLite は、シーケンス / AUTO_INCREMENT に関する**スキーマ上の差異**（SERIAL / IDENTITY の話）は持ちません。ただし上のコードのとおり pdo_sqlite も `'0'` で同じ例外を投げます。ローカルの SQLite だけで動作確認して大丈夫だったと判断するのは、いずれにせよ危険です。

## ⚠️ `DriverManager::getConnection()` が `url` を解析しなくなった

これも刺さります。DBAL 3 までは接続パラメータに `url`（DSN 文字列）を渡せば、そこから `driver` / `host` / `dbname` などを導出してくれました。DBAL 4 では `url` は解析されず、**単に無視されます**。

EC-CUBE 本体でこれが最も効いたのが `EccubeExtension::loadPlugins` です。コンテナビルド時に `dtb_plugin` を読んで「有効なプラグイン」を判定するのですが、ここが `doctrine.yaml` 既定の `driver: pdo_sqlite` を持つ設定に `url` を上書きして接続していました。

結果、DBAL 4 では url が無視されて **空の SQLite に接続**してしまい、`dtb_plugin` が読めず、**有効化済みプラグインが1件も検出されない** という状態になっていたそうです。プラグインのルート・テンプレート・Entity 拡張が一切登録されず、E2E テストが 404 で大量に落ちたと PR に書かれています。

インストーラ（`InstallerCommand::getDatabaseServerVersion` / `InstallController::createConnection`）も同様に `['url' => ...]` で接続していたため、DBAL 4 では `driver` が無く `DriverRequired` 例外で install が失敗します。

対応は、DBAL 公式の `Doctrine\DBAL\Tools\DsnParser` で `DATABASE_URL` を展開してから接続する形です。

```php
use Doctrine\DBAL\Tools\DsnParser;

$params = (new DsnParser($schemeMap))->parse($databaseUrl);
$conn = DriverManager::getConnection($params);
```

スキームマップは `DoctrineBundle\ConnectionFactory::DEFAULT_SCHEME_MAP` に準拠しています。プラグインで `DriverManager::getConnection(['url' => ...])` を書いている箇所は**確実に壊れます**。

なお `$params` には DB のパスワードが平文で入ります。デバッグ中に `dump($params)` やログ出力をしないよう注意してください。EC-CUBE の `InitDriver::connect()` に `#[\SensitiveParameter]` が付いているのも同じ理由です。

## MySQL の DDL 暗黙COMMIT × SAVEPOINT 問題

もう1つ、プラグインのインストール処理に関わる話です。

MySQL では DDL（`CREATE TABLE` など）が暗黙的に COMMIT を発行し、SAVEPOINT を破壊します。DBAL 4 の `autoCommit` 既定は `true` ですが、EC-CUBE は `TransactionListener` で `false` に設定しているため、この組み合わせでトランザクションの整合が崩れます。

4.4 の `PluginService` には、DDL 実行をラップするヘルパーが入りました。

```php
private function executeDdlWithMySqlWorkaround(Connection $conn, callable $ddlCallback): void
{
    if (!$conn->getDatabasePlatform() instanceof AbstractMySQLPlatform) {
        $ddlCallback();

        return;
    }

    $autoCommit = $conn->isAutoCommit();
    $nestingLevel = $conn->getTransactionNestingLevel();

    // MySQL の DDL は暗黙的に COMMIT を発行するため, 既存のトランザクションを
    // すべて COMMIT してからDDLを実行する.
    for ($i = 0; $i < $nestingLevel; $i++) {
        $conn->commit();
    }

    // autoCommit=false のままだと DDL 実行時に DBAL が遅延でトランザクションを
    // 開始し, MySQL の暗黙 COMMIT とずれてしまうため, 一時的に autoCommit=true にする.
    $conn->setAutoCommit(true);
    try {
        $ddlCallback();
    } finally {
        $conn->setAutoCommit($autoCommit);
        // DDL 実行前のネストレベルまでトランザクションを開始し直す.
        for ($i = 0; $i < $nestingLevel; $i++) {
            $conn->beginTransaction();
        }
    }
}
```

さらに、composer 経由の uninstall などで、DBAL のネストレベルだけが残って実接続にはトランザクションが無い、という不整合が起きることがあります。この状態で `flush()` すると、DBAL 4 では `There is no active transaction` 例外になります。これを検知して接続を閉じ、ネストレベルをリセットする `reconcileMySqlTransaction()` も追加されています。

プラグインのインストーラで `SchemaTool` を直接叩いている場合、同種の問題を踏む可能性があります。

## 4.3 → 4.4 の依存パッケージ変化（DBAL 以外も含む）

PR #6855 が実際に変えたのは `doctrine/dbal` の `^3.8` → `^4.4` と `doctrine/cache` の削除だけです。以下はブランチ同士の比較なので、他の PR の成果も混じっています。

| パッケージ | 4.3 | 4.4 |
| --- | --- | --- |
| `doctrine/dbal` | `^3.3` | `^4.4` |
| `doctrine/orm` | `^2.11` | `^3.0` |
| `doctrine/collections` | `^1.5` | `^2.1` |
| `doctrine/lexer` | `^2.0` | `^3.0` |
| `doctrine/cache` | `^2.0` | **削除** |
| `doctrine/annotations` | `^2.0` | **削除** |
| `php` | `^8.1` | `^8.2` |
| `symfony/*` | `^6.4` | `^7.4` |
| `monolog/monolog` | `^2.11` | `^3.0` |

`doctrine/annotations` が消えているのは Entity の attribute 化に対応するものです。アノテーションで `@ORM\Column` を書いているプラグインの Entity / trait は、4.4 では attribute への書き換えが必要になります。

## カスタム型を持っている場合の注意

EC-CUBE の `UTCDateTimeType` / `UTCDateTimeTzType` は DBAL 4 対応で戻り値型が変更されました。

`convertToPHPValue()` の戻り値型が `?\DateTimeInterface` から **`?\DateTime`** に変わっています。理由は PHP の戻り値共変性で、DBAL 4 で親クラス `DateTimeType::convertToPHPValue()` の戻り値型が具象 `?DateTime` に固められたためです。子クラスの戻り値型は親と同じか狭くなければならず、`DateTimeInterface`（より広い型）でオーバーライドすると `Declaration must be compatible ... : ?DateTime` の fatal error になります。

あわせて例外まわりも変わりました。

- `ConversionException::conversionFailedFormat()` → `Doctrine\DBAL\Types\Exception\InvalidFormat::new()`
- `requiresSQLCommentHint()` は削除（DBAL 4 でコメントヒント機構自体が撤廃）

独自の Doctrine Type を持っているプラグインは、この3点をそのまま確認してください。

## いま何をすべきか

4.4 はまだ未リリースですが、`4.4` ブランチはすでに動く状態にあります。プラグインを持っている方は、今のうちに以下だけでも棚卸ししておくと後が楽です。

1. 削除された DBAL API の `grep`（冒頭のコマンド）
2. `getDatabasePlatform()->getName()` の `instanceof` 化
3. `DriverManager::getConnection(['url' => ...])` の `DsnParser` 化
4. 独自 Doctrine Type の戻り値型・例外クラス
5. PostgreSQL 利用環境なら、シーケンス名を組み立てているコード
6. Entity / trait のアノテーション → attribute 移行

特に 3 と 5 は、コードは動くのに結果が静かに間違うタイプです。テストが通っても安心できません。EC-CUBE 本体でさえ、E2E が大量に落ちるまで「有効なプラグインが 0 件になっていた」ことに気付けませんでした。自分のプラグインなら、なおさらテストだけでは見つかりません。

:::message alert
EC-CUBE 4.4 はこの記事を書いている時点（2026年7月）で未リリースです。`4.4` ブランチにマージ済みの内容をもとに書いていますので、リリース時には細部が変わる可能性があります。
:::
